# lio_scan: CPU en la NX (2026-11-23)

**Problema.** En L1 `static` (bag `2026-11-19_11-24-06_static`) `lio_scan` usó **125 % de un núcleo** de media en la NX (un solo PID, 110-135 % estable, coherente con la CPU total), FAST-LIO solo 16 %. La pila de localización sumó 153 % (criterio ≤ 150 %).

**Causa: hilos de OpenBLAS girando.** La NX tiene dos numpy: la del sistema (apt 1.21.5, enlazada a `openblas-pthread`) y una 2.2.6 de pip en `~/.local` (instalada el 2026-10-19 con torch y ultralytics, con su propio OpenBLAS), que normalmente tiene prioridad. Con la del sistema, los productos `(N,3) @ (3,3)` de cada nube despiertan el pool de OpenBLAS y sus hilos se quedan girando entre nubes.

**A/B en la NX** (`nx_lio_scan_ab.sh`: bringup en marcha y robot quieto, cada variante como nodo extra con `/scan` remapeado, CPU del proceso en 30 s):

| variante | numpy de pip (2.2.6) | numpy del sistema (1.21.5) |
|---|---|---|
| original (3ac81e2) | 22.8 % | **303 %** (3 hilos al 98 %) |
| original + `OPENBLAS_NUM_THREADS=1` | 22.5 % | 25.5 % |
| con micro-optimizaciones (041b9d7) | 26.3 % | 26.3 % |

Qué numpy usó el nodo el día 19 no se puede saber a partir del bag. El 125 % encaja con la del sistema y menos hilos girando, pero queda sin demostrar: el lanzamiento tuvo que saltarse `~/.local` (otro usuario, `sudo`, otro entorno).

**Cambio** (`src/go2w_bringup/scripts/lio_scan.py`): solo `OPENBLAS_NUM_THREADS=1` (y `OMP_NUM_THREADS=1`) antes de importar numpy. Así el coste no depende de qué numpy encuentre el nodo. Las micro-optimizaciones de 041b9d7 (filtrar primero por altura, `lexsort` en vez de `np.minimum.at`, `array.array` para los rangos) se han quitado: en el PC hacían `on_cloud` 2× más rápido con el `/scan` idéntico (1210/1210, `scripts/validation/lio_scan_equivalence.py`), pero en la NX no ahorran nada. Allí el coste es casi todo el propio rclpy.

**Lecciones**
- El coste de un nodo Python depende de la numpy que encuentre, y un `pip install` lo cambia sin tocar el repo. Conviene apuntar la versión de numpy de cada nodo en el `meta.yaml` de las pruebas.
- numpy 2 en `~/.local` junto a ROS Humble (compilado con numpy 1.x) puede romper paquetes como `cv_bridge`.
- Los demás nodos Python con numpy de la pila tienen el mismo riesgo. No se pone `OPENBLAS_NUM_THREADS=1` en `env.sh` porque afectaría a YOLO (torch).

**Versión C++** (`src/go2w_bringup/src/lio_scan.cpp`, `go2w.launch.py lio_scan_cpp:=true`). Es una copia del algoritmo de `lio_scan.py`, con los mismos parámetros y comparaciones. Se compara con la versión Python recibiendo las dos a la vez el mismo replay (`/cloud_registered` + `/Odometry` del pasillo): **1210/1210 scans idénticos bit a bit** (874 830 haces, 0 diferencias, misma cabecera). CPU en el PC, en vivo con FAST-LIO: Python 15.4 %, **C++ 2.8 %**. Falta medirla en la NX.

**L1 `static` en la NX con cada versión** (2026-11-23, seguidas, mismo sitio, commit 454aab9, numpy 2.2.6):

| | `lio_scan.py` (11-37-20) | `lio_scan_cpp` (11-44-15) | referencia 11-19 (original) |
|---|---|---|---|
| `lio_scan` CPU media / p95 | 38 / 41 % | **6 / 8 %** | 125 / 134 % |
| pila de localización | 81 % | **48 %** | 153 % (FAIL) |
| NX total (8 núcleos) | 22.2 % | 17.9 % | 28.7 % |
| frecuencia media de CPU | 1085 MHz | 998 MHz | 1528 MHz |
| potencia `VDD_IN` | 5.6 W | 5.4 W | 6.8 W |
| latencia LIO p50 / p95 | 15.3 / 20.4 ms | 15.2 / 20.5 ms | 10.9 / 17.4 ms |
| deriva xy / yaw por 5 min | 1.2 cm / 0.14° | 0.08 cm / 0.02° | 0.2 cm / 0.05° |
| jitter xy / yaw p95 | 3.5 cm / 1.05° | 1.7 cm / 0.55° | 1.6 cm / 0.7° |

- Con C++, `lio_scan` cuesta 6.3 veces menos. La comparación es justa porque las dos sesiones tuvieron un reloj parecido; el de C++ fue incluso algo menor, lo que infla su %.
- Con pocas cargas el gobernador baja el reloj: el mismo trabajo sale con más % de CPU y más latencia. Por eso hoy FAST-LIO marca 26 % y una p50 de 15 ms, frente a 16 % y 11 ms el día 19, cuando el 125 % de `lio_scan` mantenía el reloj alto. Los % solo se comparan entre sesiones con un reloj parecido (`hw_nx_cpu_mhz_mean` en el informe), o fijando el reloj con `jetson_clocks`.
- El jitter de la sesión Python fue el doble y constante durante los 5 min, sin ningún evento aislado. No viene de `lio_scan`, que no alimenta a FAST-LIO (misma latencia). Varía entre arranques (de pie, inicialización de FAST-LIO). La deriva es despreciable en los tres casos.

**Siguiente.** Usar `lio_scan_cpp` por defecto y seguir el protocolo (L2-L4, EasyNav) con él.
