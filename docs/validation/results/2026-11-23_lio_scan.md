# lio_scan: CPU en la NX (2026-11-23)

**Problema.** En L1 `static` (bag `2026-11-19_11-24-06_static`) `lio_scan` usó **125 % de un núcleo** de media en la NX (p95 134 %), FAST-LIO solo 16 %. La pila de localización suma 153 % (criterio ≤ 150 %). Reproduciendo en el PC el mismo nodo costaba ~16 %.

**Cambios** (`src/go2w_bringup/scripts/lio_scan.py`). Todos dejan el `/scan` idéntico:
- BLAS limitado a un hilo (`OPENBLAS_NUM_THREADS=1` antes de importar numpy). Un nodo Python no pasa de ~100 % salvo que haya hilos fuera del GIL; la sospecha es el pool de OpenBLAS de la NX girando entre nubes. **Pendiente de confirmar en la NX.**
- Altura primero: x, y, rango y ángulo solo para los puntos dentro de la banda (la mayoría del L1 es suelo).
- `np.minimum.at` (muy lento en numpy < 1.25; la NX y el PC tienen 1.21) sustituido por ordenar por haz y rango.
- `LaserScan.ranges` se asigna como `array.array` (evita la comprobación elemento a elemento de una lista).

**Equivalencia** (`scripts/validation/lio_scan_equivalence.py`, PC i7-12700F, bag del pasillo 2026-10-28 reproducido por FAST-LIO, 1210 nubes de ~3860 puntos):

| | versión anterior (3ac81e2) | nueva |
|---|---|---|
| `/scan` idéntico | — | 1210 / 1210, diferencia máxima 0 m |
| `on_cloud` media / p95 | 2.04 / 2.24 ms | 1.00 / 1.18 ms |
| nodo completo en ROS (CPU del proceso, 60 s) | 15.7 % | 10.7 % |

El PC usa la BLAS de referencia (un hilo), por eso allí la mejora es pequeña y no explica el 125 % de la NX.

**Siguiente.** En la NX: `nx_lio_scan_check.sh` (qué BLAS usa numpy y CPU por hilo de `lio_scan`) y repetir L1 `static` 5 min con esta versión como medida de "después".
